# The owner device says on the bus whether it can act

The Sensor publishes **`fr.linagora.twalk.owner.device.state.changed.v1`** about the device Twalk acts through (ADR 0025's *owner device*): `present` when it holds a usable one, `credential_gone` when the homeserver no longer knows its token, `not_configured` when it was given none — the first event of every run carrying the state it starts in, exactly as a collector's `connection.status.changed.v1` does, so a consumer reads a run's first event as the state and not as a change. The Companion Gateway **follows that subject** — `DeliverPolicy::Last` for the cold start, then live — keeps the last state in memory and nothing else, and answers `Delivery { reach: cannot_reach, detail: owner_device_credential_gone }` for a **bridged** conversation while that state is `credential_gone`, so the approval screen stops offering a delivery this deployment can no longer perform before the owner presses anything ([#404](https://github.com/linagora/twalk/issues/404), [#229](https://github.com/linagora/twalk/issues/229)'s own words). A **native Matrix** conversation is untouched and says nothing: no bridge stands between the room and its reader, so a reply there goes out as the Sensor's own account and always did (ADR 0009). The state is **not** stored: the bus holds the last event, the Sensor republishes at every start, and a Gateway that has heard nothing answers `unknown` rather than guessing — an absence must not read as a revocation.

Rationale: the fact had no way to cross, and #404 was opened rather than guessed at inside #229 because the two shapes available are a decision and not an implementation detail. The alternative was the **Gateway reading the Sensor's `/metrics`**, where `twalk_sensor_owner_device_credential_gone` already renders. It is rejected on three counts. `SENSOR_METRICS_LISTEN` is **optional** and unset by default, so the Gateway would depend on an endpoint an operator may not have exposed and would have to degrade to a guess when it is not there — and the degradation would be invisible, which is the class of defect this project keeps closing. `/metrics` is an **operator surface**, not a contract: nothing promises a gauge's name across versions, and a Prometheus exposition is scraped rather than subscribed, so the Gateway would poll a second endpoint on a second schedule to learn a fact that changes twice a year. And it would be the **first dependency** between the Sensor and the Gateway in that direction; every other fact that crosses this deployment crosses on the bus, from consent state (ADR 0010) to a bridge's own status to a connection's — the shape is not a preference here, it is the deployment's one integration seam. A contract type costs a schema, a fixture and a projection; it buys a fact that arrives without being asked for, that a third-party consumer can read on the same terms as a first-party one (ADR 0008), and that carries the operator's remedy in the event rather than in a log nobody is reading. The **Sensor** publishes it because the Sensor is the only process that knows: it holds the credential, it is what the homeserver refuses, and #229 already made it read `M_UNKNOWN_TOKEN` for what it is. That a component publishes the state of a credential it holds is not new — the collector does exactly that for its connections (ADR 0033) — and the Sensor publishing about *itself* rather than about a conversation is the one novelty, which is why the event names no contact, carries no `consent` extension and no `network`, and is therefore never a persona's trigger (the SDK's allowlist).

The costs are accepted rather than argued away. **A new contract type before v1.0**, which is the price of the seam being the bus; it is `v1` and every breaking change increments the suffix (ADR 0007). **The state is in memory**, so a Gateway restarted while the Sensor is down and the last event has expired from the bus answers `unknown` and the screen offers the button again — a ninety-day silence from a Sensor that never restarts (ADR 0037), which is the same bound every bus consumer inherits and which the Sensor's own republication at each start makes unreachable in practice. **`unknown` is the honest default and it is not free**: an owner whose Gateway has heard nothing is offered a delivery that may fail, exactly as today, and the alternative — treating silence as a revocation — would refuse every reply on a deployment whose Sensor has simply not been restarted since the retention window. **The approval screen gains a second `cannot_reach` sentence**, because the one #216 wrote states the wrong situation as a fact — *"your account is not in this conversation"* — while here the account may well be in it and the device that would post as them is what is gone; two obstacles with one sentence would have told an owner to join a room they are already in, so `Delivery::CannotReach` now names its `Obstacle` and the Companion and the clerk choose the sentence from the same word. **The screen and the log now say one situation two ways on purpose**: the log's sentence is the operator's (`provision-owner-device.sh`, and a restart), the screen's is the owner's (onboard again in the Companion, which since [#228](https://github.com/linagora/twalk/issues/228) needs no restart), and `owner_device::REVOKED_REMEDY` is amended to name both so that neither reader is told only about the other's remedy. **Re-provisioning clears it with no other step**: the Sensor publishes `present` when it next holds a usable device — at startup, or the moment a handover arrives (#228) — the Gateway's next delivery read answers `can_reach` again, and the approval queue's next read is that read — this screen deliberately does not poll, because a list that reordered itself under a finger about to press approve is the worst thing an approval queue can do, so what clears the warning is the reader's own refresh and never a restart or a reinstall. And **this event is about the deployment's one owner device and not about a device list**: it carries the device id for an operator's eye, never a token, and a consumer that wanted to know *which* devices the owner holds would have to ask the homeserver as them, which no component here can do (ADR 0011).
